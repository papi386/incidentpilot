# V1.3 ExecutionBackend Security Specification

Status: **mandatory design/acceptance criteria for V1.3**. No shell, filesystem-write, arbitrary fetch, patch execution, or child-agent capability may ship until its applicable requirements are implemented and adversarially tested.

The goal is not to claim zero-day immunity. The goal is to make compromise of one parser/model/tool insufficient to obtain secrets + arbitrary execution + privileged repository writes + unrestricted network access together.

## Enforcement chain

Every future model-requested action must pass through this chain:

```text
LLM output
  -> strict schema validation
  -> runtime policy engine
  -> capability + resource/budget check
  -> human approval where risk class requires it
  -> tool broker
  -> isolated execution backend
```

The model is never the enforcement point and never receives raw credentials.

## 1. Network / SSRF / DNS-rebinding requirements

URL-string validation alone is forbidden for privileged outbound tools.

The outbound broker must:

1. accept only explicitly allowed schemes (normally HTTPS);
2. reject embedded credentials and unexpected ports;
3. resolve DNS in the trusted broker, not inside model-controlled code;
4. reject every resolved IPv4/IPv6 address in loopback, private, link-local, multicast, unspecified, benchmark/test, and cloud/container metadata ranges;
5. pin the connection to the validated address so DNS cannot change between validation and connection (TOCTOU/DNS rebinding);
6. retain the expected hostname for TLS/SNI/certificate verification;
7. repeat the full resolve/classify/pin process for every redirect;
8. cap redirects, response bytes, time, request count and concurrency;
9. deny outbound network access from sandboxes by default and expose only brokered egress;
10. never forward IncidentPilot/GitHub/model credentials across redirects or to repository-chosen destinations.

Metadata endpoints such as link-local instance metadata must be unreachable even if a hostname initially resolves to a public address.

## 2. Filesystem confinement / symlink requirements

Model-generated paths are untrusted data.

The execution/filesystem broker must:

- operate under an explicit workspace root;
- reject absolute paths and traversal outside that root;
- canonicalize parent paths;
- use no-follow/open-at-style primitives where the execution platform supports them;
- validate the opened object/file descriptor rather than trusting only a pre-open pathname check;
- reject symlink/junction/reparse-point escapes, including race conditions where the path changes after validation;
- never mount host/control-plane secret directories into an untrusted workspace;
- separate read, create, modify and delete capabilities rather than granting a generic filesystem tool;
- cap file count, byte size and patch size.

A repository-created symlink may never turn a workspace read/write into a host secret read/write.

## 3. Environment and credential isolation

Execution environments must start from an allowlisted environment built from scratch.

Forbidden:

- inheriting the parent Worker/runner/process environment wholesale;
- exposing GitHub App private keys, installation tokens, webhook secrets, encryption keys, session secrets or model-provider master credentials to repository code;
- passing credentials through command-line arguments or logs when a narrower secret injection mechanism exists.

If a verification task needs repository access, issue the smallest short-lived credential possible and remove it before executing untrusted repository code whenever feasible.

## 4. Repository instructions and prompt injection

Repository content, including `.md`, agent configuration, source comments, CI logs, issues, diffs and tool output, remains:

```text
instruction_trust = NEVER_INSTRUCTIONS
```

No repository file may enable shell, network, extra tools, broader filesystem access, higher budgets, child agents or approval bypasses.

Configuration affecting capabilities must come from the trusted control plane and be cryptographically/authentication-bound to the authorized user/repository policy.

## 5. Shell/process execution

Shell capability defaults OFF. The V1.2.3 domain port intentionally exposes no free-form shell-command field; it carries a typed verification capability plus argv data and `DENY_ALL` network policy. V1.3 must preserve or further narrow that contract rather than widening it to generic shell execution.

When a future risk-approved execution requires commands:

- prefer typed tools or fixed executable + argv over free-form shell strings;
- do not use `shell=true` unless explicitly justified;
- separate executable and arguments;
- use allowlists/risk classes;
- cap process count, CPU, memory, disk, output bytes and wall time;
- prevent background/daemon persistence;
- disable privilege escalation and host namespace access;
- treat command output as untrusted evidence, not instructions;
- require independent approval for privileged commands rather than allowing text/shell tricks to satisfy the approval gate.

## 6. Child-agent privilege non-inheritance

Creating a child/sub-agent must never clone the parent's full authority automatically.

Each child receives:

- a new identity/capability set;
- equal-or-narrower repository scope;
- equal-or-lower risk ceiling;
- its own request/token/tool budgets;
- no raw parent secrets;
- trace linkage back to the parent decision.

Privilege amplification by delegation is forbidden.

## 7. Tool result integrity

Tool output must carry provenance and execution identity. The model cannot fabricate a tool success record that the control plane treats as executed.

Sensitive actions require server-side verification of:

- action/tool ID;
- normalized arguments;
- repository/incident binding;
- approval binding where applicable;
- execution result/digest;
- expiration/replay state.

## 8. Adversarial acceptance tests

Before V1.3 execution tools are enabled, tests must include at minimum:

- DNS rebinding / validation-to-connect address change;
- IPv4 and IPv6 loopback/private/link-local/metadata destinations;
- redirect from allowed public URL to prohibited IP/host;
- mixed/encoded IP representations;
- symlink/junction escape and path-race fixtures;
- repository file requesting shell/network/secrets;
- command injection through tool arguments;
- parent environment secret leakage test;
- approval replay/substitution;
- child-agent privilege escalation attempt;
- oversized output/fork/resource exhaustion;
- malicious/fake tool output;
- sandbox crash/timeout/retry without duplicate privileged effects.

Zero unauthorized privileged actions and zero secret exfiltration are hard acceptance targets.

## 9. Operational response

The control plane must be able to disable model calls, privileged actions and execution backends independently. Security telemetry should identify anomalous denied requests without logging credentials or sensitive evidence plaintext.

If a new zero-day affects the execution backend, the expected first response is to disable the affected capability while preserving read-only incident ingestion/evidence collection where safe.
